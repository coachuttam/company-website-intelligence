**Verification-method note, added 2026-09-27 after the Azentio lesson below:** a page fetching
fine via WebFetch/a browser does NOT mean this project's own crawler (`wi/crawl/fetch.py`'s httpx
client, run from Uttam's actual Python/OpenSSL environment) can reach it -- WebFetch and a real
browser both fetched azentio.com's homepage and robots.txt without issue, but the real crawler
failed outright with a TLS handshake error. From here on, a candidate is only really "verified"
once a live `python run_site.py <url>` run on Uttam's machine confirms pages actually get fetched
-- WebFetch/browser checks are still useful for a first content-fit pass, just not sufficient
on their own to lock a site in.

## Follow-ups (none of these block locking the list -- both H5 and H10 are now filled)

1. **D2 Darwinbox** and **H7 NoBroker** — both look like real candidates for the JS-only fallback (B-16) to actually trigger on, beyond the intentionally-JS-heavy D7 Linear. Worth a live check once the LLM provider/key are configured (Day 1 gate) and a real Day 5 baseline run happens.
2. **H2 Buffer** — robots.txt blocks several specific AI-bot user agents by name (ClaudeBot, PerplexityBot, OAI-SearchBot). Confirm this project's crawler User-Agent string (`CompanyWebsiteIntelBot/0.1`, see wi/crawl/fetch.py) isn't one of the blocked ones -- it isn't today, but worth a periodic recheck if the UA string ever changes.
3. **H5 Temenos and H10 Renaissance Technologies** — both closed out. Unlike the earlier "worth a spot-check" framing, both have already had their live-crawl spot-check done and passed as part of locking them in (Temenos: 25 pages, 0 robots skips; Renaissance: 8 pages, 0 robots skips) -- no further action needed here.
4. **Old-LibreSSL vs. modern-TLS-only sites** (found 2026-09-27, while replacing H5) — Uttam's `.venv` links Python's `ssl` module against LibreSSL 2.8.3 (the stock macOS system Python's library; `urllib3` v2's own warning says it wants OpenSSL 1.1.1+). azentio.com's server flatly rejected the TLS handshake this produces (`TLSV1_ALERT_PROTOCOL_VERSION`), while temenos.com, rentec.com and every other benchmark site tried so far accepted it fine -- so this isn't a universal blocker, but it's a real, environment-specific failure mode distinct from robots.txt/bot-blocking (finastra.com's HTTP 403 rejection above is that separate, more common failure mode) that could silently disqualify a future site pick, or a real held-out site in Week 4, for a reason that has nothing to do with the site itself. Worth Uttam fixing at some point (reinstalling Python via Homebrew/pyenv so it links against a modern OpenSSL build) rather than working around per-site -- not urgent since only 1 of 7 externally-tried candidates has hit it so far, but flagged here so a future TLS failure isn't mistaken for a site-specific problem.
